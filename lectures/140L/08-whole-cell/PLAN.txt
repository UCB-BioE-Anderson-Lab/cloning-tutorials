HOW THE COLOUR CONVERSION IS DONE — DO NOT RECOLOUR PIXELS
----------------------------------------------------------
Most of this deck's art is still VECTOR inside the .pptx, so the pixels
are never touched.  Per AUTHORING.txt, "WHERE THE FIGURE IS STILL
VECTOR IN THE SOURCE .pptx": rewrite the theme colour scheme, re-render,
re-crop.

    python3 docs/lectures/tools/recolour_pptx.py "<source.pptx>" <scratch>
    cd <scratch> && soffice --headless --convert-to pdf recoloured.pptx \
        --outdir .
    pdftoppm -png -r 80 recoloured.pdf pages/p

Then crop each figure out of pages/p-NN.png.

TWO THINGS THAT COST TIME HERE, both now handled by the tool:

  THIRTEEN THEMES AND TEN THEME OVERRIDES.  Editing theme1.xml alone
  changes almost nothing.  207 colour slots had to move.

  THE DRAWN FIGURES BYPASS THE THEME ENTIRELY.  The cell fields are
  literal FF0000 and FF8989 on the shapes themselves, not schemeClr
  references, so a theme-only rewrite leaves every cell pure red.  The
  tool rewrites literal hexes across slides, layouts, masters and notes
  as well.  FF8989 maps to a pale tint of vermillion rather than to a
  second palette colour, because the pair is one hue at two
  brightnesses — that contrast IS the slide's argument.

  ImageMagick cannot rasterise the PDF without ghostscript, which is
  not installed on this machine.  pdftoppm does it.


TRAPS ALREADY HIT IN THIS DECK
------------------------------
REPACKING THE .pptx FROM SCRATCH PRODUCES A FILE LIBREOFFICE SILENTLY
REFUSES.  `zip -r` over the unpacked tree yields no PDF and no error
worth reading.  Copy the original and `zip` the changed XML into the
copy instead; the tool does this.

THE OTIS ENGRAVING HAS AN ALPHA CHANNEL.  Dropped straight onto the
amber section ground it turns into a muddy yellow block — the engraving
is black line work on transparency.  Flattened onto white it reads as a
mounted plate.  Any source image on a coloured ground needs this check:

    magick identify -format "%A" img.png        # Blend means alpha

CROPPING A FIGURE: trim is not enough on its own.  The DBTL cycle sits
lower on the slide than it looks, and a crop box that stops at the
title's natural margin cuts the bottom box in half.  Crop generously
below the title, then -fuzz 3% -trim, then add a white border back.

HOW SECTIONS 01-05 WERE CROPPED: A WHITE-GROUND RENDER
------------------------------------------------------
Source slides 12-40 sit on a dark grey master ground; 1-11 mostly did
not.  Cropping a drawn figure off the grey render carries the grey with
it.  So a second copy of the deck was rendered with a white <p:bg>
injected into every slide 12-40, at 160 dpi (1600x1200 px, i.e. EMU *
1600/9144000), and drawn figures were cropped from that.

What that render also had to change, all in the scratch copy only:
  - the three charts (ppt/charts/chart1-3.xml) set their axis text in
    bg1, white on the old ground.  Rewritten to ink.
  - source 33's well walls were a 20% tint of accent1, invisible on
    white -> solid blue.  Its substrate label and arrow -> ink.
  - source 35/36's promoter labels (tx2) -> ink; 35's caption tint
    removed; 36's GFP and PBAD boxes widened, because LibreOffice
    breaks "GFP" into "GF / P" where PowerPoint does not.
  - text that is set as HTML on the slide was dropped from the render,
    so it does not ride along inside a crop.
  - source 33's four build states were rendered as four separate
    slides (the well alone; + substrate; + cells; washed), each
    cropped with the SAME box and no trim, so they swap in register.

Two traps from this, both cost a re-render:
  - `zip` run with cwd= the scratch tree resolves a RELATIVE archive
    path against that cwd.  Pass an absolute destination or the archive
    silently is not updated and the "new" render is the old one.
  - swapping <a:schemeClr ...> for <a:srgbClr .../> with a plain string
    replace leaves an orphaned </a:schemeClr> whenever the scheme colour
    carries lumMod/lumOff children.  Replace the whole element.
